# Android通知学習モジュール

状態：Kotlinソース実装。ビルド、APK、エミュレーター、実機検証は未実施。このWindows環境ではJRE 8のみ確認、JDK 17・Android SDK・adbは未確認/未導入。Windows受信箱との接続も未実装。

## 実装したPhase A

`LearningListener` はNotificationListenerServiceの公開コールバックだけを使う。最初はすべてのアプリが無効。MainActivityからLINE、Instagram、Messenger、Slack、Gmail、Outlook、Discordを個別に許可する。通知アクセス設定へ誘導する。通知を勝手に消したり、元アプリの設定を変更しない。アクセシビリティ権限を要求しない。

保存情報：アプリ、チャンネル、通知キーのハッシュ、観測開始時刻、元のpostTime、タイトル、本文、更新回数、削除時刻、Androidが返した消去理由、反応までの時間、統合アプリ内確認、優先度と理由。ショートカットIDがあればアプリ・チャンネルと組み合わせたハッシュで関連づけ、なければアプリ・チャンネルの集計だけにする。タイトル一致で別人を同一人物と推測しない。通知再利用キーは削除済みepisodeと分ける。

## 取得可否

| 指標 | 方針・制約 |
| --- | --- |
| タップ | REASON_CLICKで通知が消えた場合だけ「確認できたタップ」と記録。すべてのタップを捕捉する保証なし |
| 消去 | REASON_CANCEL / REASON_CANCEL_ALLだけをユーザー消去として集計。アプリ側の消去等は区別 |
| 反応時間 | 観測開始から削除まで。時計変更、再起動、リスナー再接続で不正確になる場合を明示 |
| 展開回数 | 取得しない。公開APIで正確な回数を得たことにしない |
| 相手・グループ | 安定IDがある場合に限る。タイトルは表示用で本人識別の根拠にしない |
| 返信 | 他アプリでの返信は取得しない。将来の統合アプリの返信イベントを代替にする |
| 通知本文 | ロック状態・Androidバージョン・機密通知保護・アプリの通知形式で欠落する |

[Android公式リファレンス](https://developer.android.com/reference/android/service/notification/NotificationListenerService)がREASON_CLICKを定義しているが、通知が残るタップをすべて提供するAPIではない。Android 15の[機密通知保護](https://developer.android.com/about/versions/15/behavior-changes-all)も考慮する。

## 保存と除外

本文をスコアリング/書き込みする前に認証・OTP・パスワード等を検査し、該当通知は保存しない。4〜8桁の数字にも保守的に反応するため、日程や金額なども除外する場合がある。検出は完全ではなく、任意の長い秘密文字列を保証して除外するものではない。空の本文は保存しない。AndroidKeyStore AES-GCMで暗号化し、noBackupFilesDir内にAtomicFileとして保存する。バックアップを無効化。最大14日・500件。履歴全消去をUIから実行可能。復号失敗時は上書きを避ける。

## 評価

基準50点。ユーザーの優先指定・キーワードは100点。依頼・緊急キーワード+25。20件/7日以上の観測後に、確認できたタップ率・2分以内の反応・アプリ内確認を加点する。消去が多いだけでは15点までの減点で、単独では低重要度にならない。大量通知かつ低閲覧が重なると追加減点。75以上=高、35未満=低、その間=中。スコアは通知配送へまだ適用しない。

整理提案は観測期間・件数・確認タップ・消去件数を表示し、設定画面を開く/今回は見送る/今後表示しないを提供する。アプリ別の常に優先は設定画面で戻せる。「今後表示しない」の個別取消UIは未実装。Gmailフィルタ、迷惑メール報告、ブロック、ミュートの外部変更は実装していない。

## 再起動とバックグラウンド

NLSのシステム再バインドとonListenerConnectedで現在通知を再観測する。復帰時の一覧を新着着信と断定せず、観測時刻とpostTimeを分ける。force-stopやOEM省電力制限、権限取り消し、仕事用プロファイル等は実機テストが必要。欠落分を復元したと扱わない。フォアグラウンドサービスや独自の永続ポーリングは使わない。

## Phase B（設計のみ）

Nodeコアで同期したメッセージIDを重複排除キーにして配送する。Android端末側は高・中・サイレントの通知チャンネルで表示し、自アプリの確認・返信・消去を同じイベントモデルへ記録する。通知権限、端末間認証、FCM/APNsまたは自宅常時稼働経路、配信遅延・取りこぼしの検証が必要。元アプリの通知を切るとNLSから取得できないため、直接接続の健全性が確認できるまで切替を勧めない。
